# ADR-007: PgBouncer z transaction pooling między api a PostgreSQL

- **Status:** przyjęte (2026-10-23, wdrożone 2026-10-24) · EN: [../../en/adr/007-pgbouncer-transaction-pooling.md](../../en/adr/007-pgbouncer-transaction-pooling.md)
- **Kontekst:** jeden connection string zasila dziewięć modułowych `DbContext`ów i Dapperowy `SqlConnectionFactory`, a pula Npgsql otwiera do domyślnych 100 fizycznych połączeń, dokładnie tyle, ile wynosi domyślne `max_connections` PostgreSQL. Zmierzony 30-sekundowy sztorm 2000 żądań na sekundę rozpędził pulę do wszystkich 100 połączeń i zostawił je uśpione po przebiegu, więc nawet administracyjny `psql` został odbity z "sorry, too many clients already". Jedna instancja api potrafi zagłodzić całą bazę, a druga nie znalazłaby wolnego miejsca. Kod jest zgodny z transaction pooling (bez advisory locków, stanu sesji, LISTEN/NOTIFY i prepared statements), a blokada migracji w Npgsql EF 10 okazała się `LOCK TABLE "__EFMigrationsHistory" IN ACCESS EXCLUSIVE MODE` wewnątrz transakcji migracji (`LockReleaseBehavior.Transaction` w `NpgsqlHistoryRepository`), nie sesyjnym advisory lockiem, jak plan pierwotnie zakładał, więc migracje też przeżywają transaction pooling.
- **Decyzja:** `edoburu/pgbouncer:v1.26.1-p0` dołącza do sieci `data` jako dziewiąta usługa, a api dociera do postgresa wyłącznie przez `pgbouncer:6432`, razem z migracjami startowymi, z jednym connection stringiem i bez osobnego `MigrationConnection`. `Infrastructure/pgbouncer/pgbouncer.ini` ustawia `pool_mode = transaction` z rozmiarami właściciela, `default_pool_size = 25`, `reserve_pool_size = 10` (sięgane po 5 s czekania), `max_db_connections = 40` jako sufit dla wszystkich pul razem i `max_client_conn = 500`, więc jedna instancja api kosztuje postgresa najwyżej 35 ze 100 miejsc. Uwierzytelnianie zostaje przy SCRAM, entrypoint obrazu zapisuje `userlist.txt` z `DB_USER` i `DB_PASSWORD`, a nieznany parametr ini jest fatalny na starcie, co zweryfikowano na żywo literówką w `max_db_connections`. Api zostawia pulę Npgsql włączoną i dodaje `No Reset On Close=true`, zalecenie Npgsql dla trybu transaction. Obie pule robią różne rzeczy, Npgsql oszczędza uścisk dłoni TCP i SCRAM na zapytanie, a PgBouncer racjonuje połączenia serwerowe, a bez tej flagi każde oddanie połączenia wysyłałoby `DISCARD ALL`, które czyści połączenie serwerowe współdzielone z innymi klientami. Host failuje teraz szybko na starcie, gdy brakuje `ConnectionStrings:DefaultConnection`, zamiast rejestrować dziewięć modułów z nullowym stringiem. Testy uruchamiają prawdziwy obraz przez Testcontainers. Wszystkie dziewięć kontekstów migruje od zera przez poolera, 40 równoległych śpiących klientów obsługuje dokładnie 25 połączeń serwerowych w `SHOW POOLS`, a dziesięć równoczesnych rejestracji jednego emaila daje jedno 201 i dziewięć 409.
- **Konsekwencje:** pod tym samym sztormem postgres osiąga teraz szczytowo 11 backendów zamiast 100 i wraca tam po przebiegu, ogon latencji się składa (p99 z 58 ms do 1.9 ms, max z 576 ms do 132 ms) i żadna iteracja nie jest odrzucana, za cenę około 7% przepustowości (z 1738 do 1609 żądań na sekundę), bo nadmiarowe żądania czekają w kolejce poolera, zamiast konkurować wewnątrz postgresa. Przy zwykłych obciążeniach dodatkowy skok nie kosztuje nic mierzalnego, a całe api obsługują 3-4 backendy (zob. [performance.md](../performance.md)). Funkcje sesyjne są od teraz poza zasięgiem. Advisory lock, tabela tymczasowa albo LISTEN/NOTIFY wylądowałyby na połączeniu serwerowym współdzielonym z innymi klientami, więc kto je wprowadza, musi najpierw zdjąć tego wołającego z poolera. Przy jednej instancji api zysk to ochrona i gotowość na repliki, a nie szybkość, tak jak przewidywał plan. Test równoczesnej rejestracji ujawnił przy okazji, że zajęty email odpowiadał 400, więc rejestracja i provisioning botów odpowiadają teraz 409 przez nowy `EmailAlreadyTakenException`, zmiana kontraktu API odnotowana w [backend/identity.md](../backend/identity.md).
