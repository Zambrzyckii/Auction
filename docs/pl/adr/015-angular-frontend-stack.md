# ADR-015: Stack frontendu na Angularze 22

- **Status:** zaakceptowany (2026-11-08) · EN: [../../en/adr/015-angular-frontend-stack.md](../../en/adr/015-angular-frontend-stack.md)
- **Kontekst:** siedmiofazowy plan infrastruktury serwerowej jest ukończony, a backend daje klientowi przeglądarkowemu wszystko, czego ten potrzebuje, przez gateway nginx na `:8080`: 51 endpointów, jeden kontrakt `{"error":"..."}`, CORS dla `http://localhost:4200` i kandydackie widoki spisane we [frontend.md](../frontend.md). Pierwotna notatka projektowa wskazała Angulara jako framework i nic poza tym nie było rozstrzygnięte. Frontend to własny stack nauki właściciela, więc kickoff musiał rozstrzygnąć wersję, tooling, układ w repozytorium i klienckie odpowiedzi na to, czego backend nie daje: kanał push, listę "moich aukcji" i token żyjący dłużej niż swoje 15 minut.
- **Decyzja:** klient to Angular 22 z domyślnymi ustawieniami CLI, które dziś oznaczają komponenty standalone, sygnały, zoneless change detection, Vitest jako runner testów i SCSS, wygenerowany jako jedna aplikacja z `package.json` bezpośrednio w `Frontend/`, symetrycznie do `Backend/`. Stylowanie to czysty SCSS: Angular Material i Tailwind odrzucono, bo UI MVP jest celowo surowe, czytelne jedynie na tyle, by dało się testować ręcznie, a właściwy UI/UX to osobna odnoga planu na samym końcu projektu, po logice frontu, poprawkach backendu i botach AI; paczki npm spoza scaffoldu `ng new` wymagają osobnej zgody właściciela. Formularze używają Signal Forms, stabilnych od v22 i spójnych z sygnałową resztą aplikacji, z fallbackiem na Reactive Forms tylko za osobną zgodą. Dev-server dociera do API przez proxy na `http://localhost:8080` zamiast CORS, odwzorowując docelowy układ, w którym nginx kiedyś serwuje SPA z tego samego originu. Klient polluje zamiast nasłuchiwać: szczegół aukcji co 2-3 s, zgodnie z 2-sekundowym TTL cache'a odczytów Auctions (ADR-009), lista rzadziej, a każdy asynchroniczny wynik (utworzenie portfela, aktywacja aukcji, potwierdzenie bidu) jest renderowany jako jawny stan oczekiwania, a nie zakładany jako natychmiastowy. 15-minutowy token gracza obsługuje ponowne logowanie, interceptor HTTP czyści token przy 401 i przekierowuje na widok logowania z returnUrl; refresh flow pozostaje śledzony jako issue #18, bo docelowy dostawca OIDC wskazany w [infrastructure.md](../infrastructure.md) i tak by go przyniósł. Endpoint "moje aukcje" zostaje odłożony do czasu po MVP, więc pierwsze partie nie zmieniają niczego w backendzie.
- **Konsekwencje:** całe MVP buduje na istniejącym API, więc suita backendu pozostaje nietknięta, a partie frontowe weryfikują `ng build`, Vitest i ręczne próby na stacku compose. CI zyskuje job `frontend`, a dwa źródła szumu CI, które wypłynęły przy przeglądzie kickoffu, czyli test gatewaya na innej wersji nginx niż compose i obraz api wypychany do GHCR przy commitach czysto frontendowych, są na razie zaakceptowane i śledzone jako issues #19 i #20. Gracz wciąż może zostać wylogowany w środku akcji, gdy token wygaśnie, co jest zaakceptowanym kosztem do czasu refresh flow. Polling wydaje requesty zamiast połączeń i przy wybranych interwałach pozostaje daleko poniżej limitów per IP na gatewayu. Dług wizualny jest celowy: widoki pozostają zwykłym HTML-em z minimalnym arkuszem do czasu odnogi UI/UX, więc nic w tych partiach nie powstaje po to, by na to patrzeć, tylko po to, by tego używać. Toolchain obejmuje teraz Node 26 i runner Vitest w jsdom, a Dependabot pilnuje paczek npm w `/Frontend` z wykluczeniem majorów Angulara, bo te migrują przez `ng update`.
