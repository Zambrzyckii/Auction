# ADR-006: gateway nginx przed api, z limitami IP i modelem zaufania CIDR

- **Status:** przyjęte (2026-10-22, wdrożone 2026-10-23) · EN: [../../en/adr/006-nginx-gateway.md](../../en/adr/006-nginx-gateway.md)
- **Kontekst:** do fazy drugiej api publikowało własny port, więc między klientem a hostem nic nie stało. Platforma potrzebuje jednego wejścia dla planowanego frontendu i botów oraz miejsca na limity IP i limity body, które nie kosztuje hosta żadnej pracy. Za proxy host nadal musi widzieć prawdziwy adres i schemat klienta, a właściciel chce przenieść jak najwięcej przekrojowej kontroli ruchu poza aplikację.
- **Decyzja:** nginx 1.28.3 (alpine) to jedyna publikowana usługa, a cała jego konfiguracja to jeden plik, `Infrastructure/gateway/nginx.conf`. Przekazuje `/api/` i `/health`, sam odpowiada na `/gateway-health`, otwiera `/openapi/` tylko dla loopbacka i prywatnych zakresów `172.16.0.0/12` i `192.168.0.0/16`, a na całą resztę odpowiada 404. Limity działają per adres klienta w trzech strefach rozdzielonych obecnością nagłówka `Authorization`, anonimowa 20 żądań na sekundę (burst 40), uwierzytelniona 60 (burst 120) oraz logowanie z rejestracją 1 (burst 5). Odmowy wracają jako 429 z `Retry-After: 1` i ciałem JSON w kształcie `{"error":"..."}` z api, a za duże body jako 413 w tym samym kształcie. Domyślny limit body to 64 KB, a wysyłka awatara dostaje 4 MB, więc gateway nigdy nie jest surowszy od api. nginx nadpisuje `X-Forwarded-For`, `X-Forwarded-Proto` i `X-Request-Id`, kompresuje JSON od 1 KB, pisze log dostępu w JSON bez nagłówka `Authorization` i co 5 sekund odświeża adres api przez DNS Dockera. Po stronie hosta sekcja fail-fast `Gateway` wymienia zaufane sieci jako kanoniczne CIDR (literówka w rodzaju `172.16.80.1/24` to błąd startu, tak jak w kontroli samego Dockera), a `UseForwardedHeaders` działa pierwsze i ufa całej przypiętej sieci `edge` `172.16.80.0/24`, więc drugi gateway nie wymagałby zmian. `/health/live` i `/health/ready` oddzielają żywotność od gotowości, a kontener api zgłasza zdrowie przez bash `/dev/tcp` na `/health/ready`. CORS zostaje w hoście. Strefa zapisów, strefa botów po `X-Api-Key` i `limit_conn` z planu wypadły, żeby pierwsza wersja była mała. TLS jest odłożony.
- **Konsekwencje:** każde żądanie z zewnątrz przechodzi przez limity, ograniczenia body i log dostępu, a api nie ma już publikowanego portu (`compose.debug.yaml` publikuje je do debugowania na 127.0.0.1:8081). nginx nie umie zweryfikować JWT, więc fałszywy nagłówek `Authorization` daje większą pulę, a limity per użytkownik zostają w backendzie w fazie 7. W Compose i na tym komputerze wszyscy klienci mają jeden adres, więc k6 przez gateway jest trzymane na 20 anonimowych żądaniach na sekundę, a zmierzony narzut to około 0.05 do 0.1 ms na medianie (zob. [performance.md](../performance.md)). Zakres edge występuje w `compose.yaml` dwa razy, w sieci i w `Gateway__TrustedNetworks__0`, a gdy oba miejsca się rozjadą, host po cichu przestaje ufać nagłówkom. Lista `allow` dla `/openapi/` działa tylko, dopóki `edge` leży w `172.16.0.0/12`. Limit awatara wiąże nginx z `Profiles:Avatar:MaxBytes`, więc podniesienie tego ustawienia w stronę 5 MiB wymaga podniesienia też limitu 4 MB. Odtworzone api jest znajdowane w ciągu jednego 5-sekundowego okna odpowiedzi 502, a nginx odpowiada na 502 stroną HTML zamiast JSON. `Host` dociera do api bez portu, co dotyka tylko wpisu `servers` w OpenAPI. Dopóki nie wejdzie TLS (wyłącznie HTTPS z własnym certyfikatem, odnawianym automatycznie albo serwowanym przez redundantną parę), stack nie może być wystawiony do internetu.
