# ADR-014: OpenBao jako zaplecze sekretów

- **Status:** przyjęte (2026-11-04) · EN: [../../en/adr/014-openbao-secrets.md](../../en/adr/014-openbao-secrets.md)
- **Kontekst:** do fazy szóstej każdy sekret stacku żył jako jawna zmienna środowiskowa w commitowanym `compose.yaml`, a martwa para `Backend/.env` sugerowała mechanizm, który nigdy nie istniał. Aplikacja czyta całą konfigurację przez `IConfiguration`, brakowało więc źródła konfiguracji opartego o usługę sekretów. Zwykłe sekrety plikowe compose pokrywają większość higieny dla kontenerów infrastruktury, ale nie wyrażą kontroli dostępu per aplikacja ani śladu audytowego, a właściciel chciał doświadczenia najbliższego chmurowemu Key Vaultowi. Infisical odrzucono jako zbyt ciężki (własna baza plus Redis), wybrano OpenBao (fork HashiCorp Vault pod Linux Foundation, MPL-2.0, API zgodne z Vaultem).
- **Decyzja:** api czyta swoje pięć sekretów (`ConnectionStrings:DefaultConnection`, `Jwt:Key`, `Bots:ApiKey`, `Messaging:Rabbit:Password`, `Cache:Redis:ConnectionString`) z OpenBao przez ręcznie napisany `IConfigurationProvider` na około 120 linii, bez nowej paczki. VaultSharp i agenta bao odnotowano jako alternatywy i odrzucono, bo provider potrzebuje dokładnie dwóch wywołań HTTP, logowania AppRole i jednego `GET` KV v2. Sekcja `Vault` z fail-fastem domyślnie ma `Enabled=false`, więc `dotnet run`, testy i CI nigdy nie potrzebują vaulta, ten sam wzorzec co przełącznik transportu `Messaging` z ADR-013. Po włączeniu źródło jest dodawane jako ostatnie, więc wartości z vaulta wygrywają ze zmiennymi środowiskowymi, a każda awaria (nieosiągalny, 403, 404, brak plików poświadczeń, wartość niebędąca stringiem) zatrzymuje start czytelnym komunikatem wskazującym klucz konfiguracji. Sekrety leżą pod `secret/auction/api` z kluczami konfiguracji, razem z dwukropkami, jako nazwami pól KV, więc spłaszczanie to zwykłe przepisanie. Polityka AppRole, napisana przez właściciela, przyznaje odczyt dokładnie `secret/data/auction/api`. Kontenery infrastruktury nie rozmawiają z vaultem, dostają sekrety plikowe compose generowane przez `Infrastructure/secrets/gen-secrets.sh` do gitignorowanego katalogu. PgBouncer dostaje montowany, generowany `userlist.txt` zamiast obrazu z wrapperem (wybór właściciela, bez drugiego budowanego obrazu), Redis dostaje `--requirepass` z pliku (wybór właściciela, dzięki czemu connection string Redisa staje się prawdziwym sekretem), a RabbitMQ dostaje generowany plik `conf.d`, bo jego obraz twardo odrzuca warianty zmiennych `_FILE`. W compose deweloperski serwis `vault` plus jednorazowy `vault-init` seedują politykę, AppRole, sekrety i pliki `role-id`/`secret-id` przy każdym starcie stacku, a api czeka na `service_completed_successfully`. Tryb trwały raft z ręcznym odpieczętowaniem istnieje jako overlay `compose.vault-persistent.yaml` z ćwiczeniem w [operations.md](../operations.md).
- **Konsekwencje:** `compose.yaml` nie niesie już żadnych wartości sekretów, tylko odwołania, a stare pliki `Backend/.env` zniknęły. Api czyta vault raz przy starcie, więc rotacja oznacza zmianę pliku sekretu i restart łańcucha, co opisuje runbook. Awaria vaulta niczego nie zepsuje, api kończy się szybko z czytelnym błędem, a polityka restartów ponawia próby aż vault wróci, zweryfikowane na żywo. Na jednym hoście zysk jest uczciwie głównie edukacyjny, łańcuch zaufania i tak kończy się na systemie plików hosta, gdzie `gen-secrets.sh` zapisuje pliki, a wolumen Dockera trzyma poświadczenia AppRole, czyli dokładnie problem secret zero nazwany w planie. Tryb dev trzyma vault w pamięci, więc każdy restart vaulta wymaga ponownego seedu przez `vault-init`, a ćwiczenie wykazało dwie ostre krawędzie obsłużone teraz w skrypcie i runbooku, świeży trwały vault nie ma zamontowanego silnika KV, a tryb dev odmawia root tokena w formacie tokenów serwisowych `s.`. Testy pokrywają provider na fałszywym `HttpMessageHandler` i prawdziwy kontrakt AppRole na OpenBao z Testcontainers.
