# AuctionServer — changelog

> Milestone-level entries, newest first; each entry is dated by the day the work was done.

- **2026-11-01** — **Apply-once inbox**: stage seven, the last of the cleanup pass ordered after the 2026-10-24 architecture review (its candidate four). The read-exactly-once ritual copied into 39 consuming handlers (check the inbox, apply the change, add the `ProcessedMessage` row by hand, save with `CancellationToken.None`, swallow the module's `EventAlreadyProcessedException`) collapses into one shared operation: the `ProcessedMessage` entity moved to `Shared.Infrastructure/Inbox` next to the outbox entity (each module maps its own table through `ProcessedMessageModel.Configure`; the tables did not change, so the eight model snapshots were hand-edited to the new CLR name again, no migrations), and the `InboxOperation.ApplyOnceAsync` extension on the module's `DbContext` checks the inbox, runs the handler's change delegate (which may return one reply `OutboxMessage`), saves everything in one `SaveChangesAsync(CancellationToken.None)` and, when that save fails, re-reads the inbox and swallows the failure only when the `EventId` turns out recorded by a concurrent delivery (the first cut matched the violated constraint's name against the inbox primary key; the stage review replaced it with the re-read, which does not depend on which statement of the failed batch ran first). Handlers now state only what should change through their repository's one-line `ApplyOnceAsync` forward; the eight twin entities, `WasEventProcessedAsync` copies and `EventAlreadyProcessedException` types are gone, and the Application layer no longer imports module `Infrastructure.Inbox` types. The behavior change is deliberate: a unique violation of any other index used to be mistaken for a duplicate read and silently swallowed with the message marked delivered, and now it retries and, when the conflict persists, dead-letters with the real reason, which the reworked Profiles duplicate-profile test asserts. Profiles gained the `Shared.Infrastructure` project reference like every other module. Four new test methods in `Shared.Infrastructure.Tests` cover the sequential duplicate, the concurrent race (the losing transaction rolls back whole, the winner's reply survives), a race lost on a domain index that fails before the inbox insert and a foreign unique violation propagating. See ADR-012. Eleven test projects plus the support library and 876 methods solution-wide.
- **2026-11-01** — **Delivery dispatcher**: stage six of the cleanup pass ordered after the 2026-10-24 architecture review (its candidate one). Publishing splits into transport and delivery: `PublishAsync` now means only "handed over for delivery", the in-process transport calls the new `IIntegrationEventDispatcher.AcceptAsync`, which stores one row per recipient in the new `DeliveryMessages` table (composite key `(MessageId, Recipient)` making the accept idempotent; `DeliveryDbContext` with the `Add_Delivery_Messages` migration lives in `Shared.Infrastructure`), and the producer's outbox row is marked processed at that hand-off. Recipients and their order moved out of MediatR's registration-order accident into the host's explicit, strict `IntegrationEventRecipients` map, and one sequential `DeliveryProcessor` claims due delivery rows with the outbox courier's leased `SKIP LOCKED` pattern and invokes each recipient separately, so backoff retries, dead letters and the new `AuctionServer.Delivery` metrics live per recipient: a consumer's failure no longer blocks the other recipients of the same message and no longer lands on the producer's row, which is what lets phase five swap the transport without changing behavior. The hidden money-before-items ordering of `WarehouseWonEvent` became an explicit chain: Wallets charges and emits the new `WarehouseSettledEvent` (event thirty-eight) in the charging transaction, and Inventory mints the manifest from it. `SagaStage` now also waits on and fast-forwards the delivery table, and the poisoned-message saga asserts the dead letter on the recipient's delivery row while the producer's outbox row stays processed and clean. Eight new test methods in `Shared.Infrastructure.Tests` cover map order, the isolation of a failing recipient, a per-recipient dead letter, idempotent accept, the lease and cleanup. The second polling hop was measured the same day at about half a second on the median and 0.3-0.5 s on p95 (7.3-7.5 s against the 8 s threshold, see performance.md). See ADR-011; ADR-003 and ADR-005 amended. Eleven test projects plus the support library and 872 methods solution-wide.
- **2026-11-01** — **Shared outbox infrastructure**: stages four and five of the cleanup pass ordered after the 2026-10-24 architecture review. The eight hand-synchronized per-module copies of `OutboxMessage` and `OutboxProcessor` are replaced by one `OutboxMessage` entity and one generic `OutboxProcessor<TContext>` in the new shared project `AuctionServer.Shared.Infrastructure` (EF Core lives there; `Shared.Integration` stays contracts-only and remains the only contact surface between modules), each publishing module mapping its own table through `OutboxMessageModel.Configure` and registering its instance through `AddOutboxProcessor<TContext>(moduleName)`. Delivery gained a claim: `OutboxCourier.ClaimAsync` leases up to 20 due rows for 30 s in a single `UPDATE ... FOR UPDATE SKIP LOCKED ... RETURNING *` statement (one implicit transaction, safe behind PgBouncer's transaction pooling), so a second instance of a module no longer double-publishes as a matter of course; the new partial index `IX_{table}_Pending` keeps the claim off delivered rows, and `OutboxCourier.CleanupAsync` deletes rows processed more than 7 days ago once an hour, dead rows kept. The `Add_Outbox_Lease` migrations land in all eight modules; the entity move itself changed no schema, so the eight model snapshots were hand-edited to the new CLR name instead of generating eight empty migrations. The new `AuctionServer.Shared.Infrastructure.Tests` project runs the courier against a real postgres (concurrent claims take disjoint rows, a leased row is not re-claimed, cleanup deletes only processed rows past retention) and consolidates the three diverging entity-test copies; both CI pipelines run it in `integration-tests`. See ADR-010. Eleven test projects plus the support library and 864 methods solution-wide.
- **2026-11-01** — **Saga test stage**: stage three of the cleanup pass ordered after the 2026-10-24 architecture review. The new shared library `AuctionServer.TestSupport` pins the test database image to Compose's `postgres:16-alpine` (the `TestDatabase.Image` constant, now used by all thirteen database fixtures; twelve of them used to pull `postgres:latest`, so tests and the stack could silently run different database versions) and provides `SagaStage<TEntryPoint>`: one PostgreSQL container plus the whole host booted through `WebApplicationFactory` with `UseSetting` instead of process environment variables and with `Database:MigrateOnStartup=true`, so all nine contexts migrate and the background services see complete tables, and `WaitForOutboxQuietAsync`, which polls the eight outbox tables until every message is delivered and can fast-forward retry backoff so dead-lettering takes seconds instead of minutes, while all delivery stays with the real `OutboxProcessor`s. The first two cross-module tests in the repository run on it in `AuctionServer.Api.Tests`: registration enters through HTTP and is asserted across three modules (the wallet with the starting funds, the three starter items, the profile snapshot), and a poisoned `ItemLockedEvent` outbox row is retried five times and parked dead with its error history while the consumer's inbox stays empty. Phase five inherits both tests as the net that must stay green after the transport swap. Ten test projects plus the support library and 868 methods solution-wide.
- **2026-11-01** — **Warehouse entry correlation**: fix for the second of the two possible bugs reported by the 2026-10-24 architecture review, the warehouse mirror of the 2026-10-25 pending-bid fix. The entry-lock request id (the `EventId` of `WarehouseEntryLockRequestedEvent`) is now stamped on the participant as `EntryRequestId` (migration `Add_Warehouse_Participant_Request`, backfilled with `Guid.Empty`, which old payloads deserialize to as well, so in-flight sagas kept matching across the deploy), both Wallets replies echo it as a defaulted `RequestId`, and the Warehouses handlers match every reply against the stored id. Previously both replies were routed by `UserId` alone, so after a leave and rejoin the stale confirmation of the first request could activate a participant whose new fee was never locked, and worse, the stale rejection of the first request could silently remove an already confirmed participant whose fee was locked, stranding the lock forever because the rejected path emits no refund. Now a mismatched confirmation is answered with `FundsUnlockRequestedEvent` and the participant stays `PendingLock`, and a mismatched rejection only writes its inbox row. Three new test methods across Warehouses plus echo assertions in Wallets (866 solution-wide).
- **2026-11-01** — **Auction read cache**: phase four of the server-infrastructure plan. The three anonymous Auctions reads (list, detail, bid history) now pass through a TTL cache behind the module-owned `IAuctionReadCache` seam: the query records implement `ICachedQuery` (key `auctions:{kind}:v1:{arg}` and a TTL from `Auctions:ReadCache`, default 2 s, validated 1-60 s at startup), the open-generic `CachingBehavior` intercepts them in the MediatR pipeline, and `HybridAuctionReadCache` wraps `HybridCache` with `Expiration == LocalCacheExpiration`, fail-open (a cache failure logs, counts on the new `AuctionServer.Auctions.Cache` meter and falls back to the database; a factory exception propagates uncached, so a 404 is never stored) and no invalidation on write. The host's new fail-fast `Cache` section picks one of three states, off (pass-through), L1 only, or L1 plus Redis L2 through `AddStackExchangeRedisCache` (`AbortOnConnectFail=false`, 500/300 ms timeouts, instance prefix `auctionserver:`), and Compose gained `redis:7.2-alpine` (64 MB, `allkeys-lru`, no persistence, the api deliberately not depending on it) as its tenth service. Measured off against on at the frozen limits: latency unchanged with postgres under 3% CPU, a 92.6% hit ratio keeping about thirteen out of fourteen reads away from postgres, L2 nearly idle at one instance, and `visibility_lag` p95 up from 6.02 s to 7.29 s, within the bids TTL, so the owner raised the mixed.js threshold to 8 s, see [performance.md](performance.md) and [ADR-009](adr/009-hybrid-read-cache-in-auctions.md). New tests cover the wrapper, the behavior, the keys, both option sets, the module toggle and five runs against a real Redis through the new `RedisFixture`, including fail-open with the container stopped mid-test. Ten test projects and 863 methods solution-wide.
- **2026-10-25** — **Pending bid correlation and timeout**: fix for the first of the two possible bugs reported by the 2026-10-24 architecture review. The funds-lock request id (the `EventId` of `FundsLockRequestedEvent`) is now stored on the auction as `PendingBidRequestId` with the `PendingBidRequestedOn` timestamp (migration `Add_Auction_Pending_Bid_Request`), both Wallets replies echo it as a defaulted `RequestId`, and the Auctions handlers match every reply against the stored id: a reply that does not match (stale, a duplicate of an already resolved request or an old payload) answers with `FundsUnlockRequestedEvent` instead of confirming whoever happens to be pending (previously `ConfirmPendingBid` confirmed whatever was pending, and an unmatched confirmation dead-lettered), and a stale rejection only writes its inbox row. `AuctionCloser` gained a third sweep that rejects pending bids older than `PendingBidTimeout` (1 minute) and emits the same unlock, leaning on Wallets' missing-lock tolerance, so a dead funds-lock request no longer freezes the auction with 409s until `EndsOn`. Six new integration test methods across Auctions (833 solution-wide, including the read-cache seam of phase four opened the day before).
- **2026-10-24** — **PgBouncer**: phase three of the server-infrastructure plan. The new `pgbouncer` Compose service (`edoburu/pgbouncer:v1.26.1-p0`, 1 CPU, 64 MB, `data` network, healthchecked with `pg_isready`) pools connections in transaction mode with the owner's sizes in `Infrastructure/pgbouncer/pgbouncer.ini` (`default_pool_size` 25, `reserve_pool_size` 10, `max_db_connections` 40, `max_client_conn` 500, SCRAM from a generated `userlist.txt`), and the api, startup migrations included, reaches postgres only through `pgbouncer:6432` with Npgsql pooling kept on plus `No Reset On Close=true`. Migrations can go through the pooler because the Npgsql EF 10 migration lock turned out to be a table lock inside the migration transaction, not the session advisory lock the plan assumed; the plan and [infrastructure.md](infrastructure.md) were corrected. The host now fails fast at startup when `ConnectionStrings:DefaultConnection` is missing instead of registering nine modules with a null string. The new `PgBouncerFixture` starts the real image through Testcontainers for three tests: all nine contexts migrate from zero through the pooler, 40 parallel clients are served by exactly 25 server connections, and ten concurrent registrations of one email give one 201 and nine 409s, which exposed that a taken email answered 400. Registration and bot provisioning now answer 409 through the new `EmailAlreadyTakenException`, an API contract change recorded in [backend/identity.md](backend/identity.md), while login keeps its neutral 400. Measured before and after at the frozen limits: the regular scenarios are unchanged within noise and served by 3-4 backends instead of 11, and the 2000 req/s storm that used to drive Npgsql to all 100 postgres connections (leaving them idle afterwards, with an administrative `psql` refused) now peaks at 11 backends, with the p99 tail cut from 58 ms to 1.9 ms, zero dropped iterations and about 7% less throughput, see [performance.md](performance.md) and [ADR-007](adr/007-pgbouncer-transaction-pooling.md). Ten test projects and 819 methods solution-wide, a fresh count of `[Fact]` and `[Theory]` methods that also corrects the 797 carried by earlier entries, which was 19 short.
- **2026-10-23** — **nginx gateway**: phase two of the server-infrastructure plan. nginx 1.28.3 in the new `gateway` Compose service is the only entry point on port 8080, and the api lost its published port (`compose.debug.yaml` publishes it on 127.0.0.1:8081 for debugging). The single `Infrastructure/gateway/nginx.conf` proxies `/api/` and `/health`, opens `/openapi/` to loopback and private networks only, limits each client address in three zones split by the `Authorization` header (anonymous 20 r/s, authenticated 60 r/s, login and register 1 r/s), caps bodies at 64 KB with 4 MB for the avatar upload, answers 429 and 413 in the api's `{"error":"..."}` shape, overwrites `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Request-Id`, compresses JSON, writes a JSON access log without the `Authorization` header and re-resolves the api through Docker's DNS every 5 s. The host gained a fail-fast `Gateway` section with canonical CIDR validation, `UseForwardedHeaders` as the first middleware trusting the pinned `edge` network `172.16.80.0/24`, and `/health/live` plus `/health/ready` next to `/health`. The api container reports healthy through bash `/dev/tcp`, and the gateway, limited to 1 CPU and 128 MB, starts only after it. `AuctionServer.Api.Tests` gained 34 test methods, 24 of them against real nginx and traefik/whoami through Testcontainers, including a 403 for a public address on a TEST-NET subnet, and both CI pipelines got a `gateway-config` job with `nginx -t`. Probed live (forwarded-header trust from edge only, gzip on the OpenAPI document, 429s, the api found again after an address change) and measured with the new `gateway-limits.js` at about 0.05 to 0.1 ms of median overhead, see [performance.md](performance.md) and [ADR-006](adr/006-nginx-gateway.md). Ten test projects and 797 methods solution-wide.
- **2026-10-23** — **Observability and k6 baseline**: phase one of the seven-phase server-infrastructure plan adopted on 2026-10-22. The host wires OpenTelemetry behind a fail-fast `Observability` section (absent means off): traces, metrics and logs leave over OTLP, with Npgsql and `AuctionServer.*` sources and meters subscribed and `/health` filtered out. The sampler is a `ParentBasedSampler` wrapping the new `DropOrphanClientSpansSampler`, which drops every root `Client` span, because the eight outbox pollers and the keepers otherwise flood Tempo with single-span traces; two narrower tag-based variants failed against reality first (the stable semantic conventions renamed `db.system` to `db.system.name`, and Npgsql supplies no `db.*` tags at span creation, the only moment a sampler sees). Publishing is measured by the `InstrumentedEventPublisher` decorator in the host (meter `AuctionServer.Messaging`), and all eight `OutboxProcessor`s report to the static `OutboxMetrics` in `Shared.Integration`: processed, failed and dead counters per module plus a publish-lag histogram with bucket boundaries aligned to the 20/40/80/160/320 s retry tiers. `compose.yaml` grew to seven services plus an on-demand load generator, split into `edge` and `data` networks with frozen resource limits (`api` 2 CPUs and 1 GB, `postgres` 1 CPU and 512 MB): OTel Collector 0.163.2, Prometheus v3.15.1, Tempo 3.1.1 and Grafana 13.2.4 on 127.0.0.1:3000 with provisioned datasources, configured under the new `Infrastructure/observability/`. k6 scenarios under `Infrastructure/k6/` (`browse`, `bid-storm` with the domain's 409s classified as expected, `mixed` with the `visibility_lag` trend) seed their own data through the public API, survived three real eventual-consistency traps while being written (starter pack and wallet creation lag, the saga activation wait) and guard thresholds chosen from the first baseline: anonymous reads p95 around 1 ms at 50 req/s on the frozen limits, and a measured bid-visibility lag of 3-5 s that phase five is expected to cut. The baseline lives in the new [performance.md](performance.md). New host test project `AuctionServer.Api.Tests` (22 test methods, run by both CI pipelines), ten test projects and 763 methods solution-wide.
- **2026-10-22** — **Private profiles**: the deferred piece of the Profiles roadmap item, shipped the same day. `UserProfile.IsPrivate` (migration `Add_Profiles_Privacy`, default false) is flipped by the new `PUT /api/profiles/me/privacy` (51 endpoints in total), and `GetProfileQueryHandler` applies the rule at read time: the owner and accepted friends keep the full profile, a stranger viewing a private profile gets only the username, the `isPrivate` flag and the `avatarUrl`. The friendship check reuses the canonical pair lookup, the avatar route stays open because the picture is the one thing a private profile still shows, and the username stays visible because friend lists and pending requests leak it anyway. Eleven new test methods (741 solution-wide). The same commit series also pinned SSH.NET 2026.0.0 in `Profiles.Tests`, closing the last NU1903 warning.
- **2026-10-22** — **Profiles**: ninth module `AuctionServer.Modules.Profiles`, the social layer and the first consume-only module (an inbox without an outbox, no background services). Player levels are computed in Wallets from `LifetimeTurnover` (`PlayerLevels`: level `n` at `1000 * n^2`, reward `10 * n^2` paid straight into the balance, cap at level 100, rewards excluded from turnover, migration `Add_Wallets_Levels`) and emitted as coalesced `PlayerLevelledUpEvent` rows by the overridden `WalletDbContext.SaveChangesAsync`; Profiles mirrors them monotonically, so reordered retries cannot regress a profile. `UserRegisteredEvent` gained a defaulted `Username` parameter for the profile snapshot (old payloads deserialize to null, the handler falls back to `Player`). Avatars live in SeaweedFS behind the `IAvatarStorage` seam (`AWSSDK.S3`, path style, checksums `WHEN_REQUIRED`, anonymous gateway reachable only inside the Compose network, lazy bucket creation): the upload endpoint caps the request body before reading the form itself, sniffs jpeg/png/webp magic bytes (SVG rejected as XSS) and stores the SHA-256 hash that drives the `?v=` cache-buster and the ETag of the download proxy, which also sends `nosniff`. Social links are validated against per-platform domains (subdomains pass, lookalike hosts do not), friends work through requests with auto-accept on a cross request and a canonical unique pair index, and warehouse-war invites are pointer records with read-time expiry and an opportunistic purge. Twelve endpoints under `/api/profiles`, one new integration event (37 in total), five new tables (migrations `Initial_Profiles`, `Add_Profiles_Socials`, `Add_Profiles_Avatars`, `Add_Profiles_Friendships`, `Add_Profiles_Warehouse_Invites`), 84 test methods in the new project plus level and event tests in Wallets and Identity, the first non-PostgreSQL Testcontainer (SeaweedFS) and host smoke tests through `ProfilesCustomApi`. A live probe against the Compose stack passed 53 checks and caught one real bug: the avatar body limit ran after `IFormFile` binding had already read the body, fixed by reading the form manually after setting the limit.
- **2026-10-22** — **Outbox batch isolation**: every `OutboxProcessor` now publishes each message through its own DI scope instead of one scope per batch of up to 20. Previously a consumer handler that failed (for example by losing a `Version` race) left its modified entities tracked in the shared module `DbContext`, so every later message to the same module in that batch failed its save too and burned one of its five attempts. The fix is mirrored across all eight module copies, and the sender's own context still reads the batch and saves the bookkeeping.
- **2026-10-17** — **Casino**: eighth module `AuctionServer.Modules.Casino`, the first continuous money sink. Wallet money is exchanged 1:1 for casino chips through an asynchronous purchase saga with Wallets (`CasinoChipPurchaseRequested`/`Completed`/`Rejected`, debit through the existing `Wallet.Withdraw`, one purchase in flight per player through a filtered unique index, stale purchases expired by `CasinoKeeper` and a late completion still credits the chips, a recorded departure from the pawnshop's late-reply rule). Gameplay is synchronous on the chip balance: european roulette (up to 20 bets per spin, payout `stake * 36 / covered pockets`, zero loses outside bets, the pocket drawn through `ICasinoRandom`) and blackjack (Hit/Stand/Double, 3:2 naturals, dealer stands on soft 17 and peeks, a fresh six-deck shoe drawn by `ShoeCardSource` without persisting card order, abandoned hands auto-stood by the keeper). Cash-outs flow through the new `Wallet.ReceiveCasinoCashOut` and never build `LifetimeTurnover`, closing the hedging exploit. The blackjack edge was measured on 10M seeded hands of the real domain (1.084 % of the initial stake, anchored by the closed-form natural probability 4608/97032). Eight endpoints under `/api/casino`, four new integration events, seven new tables (migrations `Initial_Casino`, `Add_Casino_Roulette` and `Add_Casino_Blackjack`), 104 test methods in the new project plus 8 in Wallets. A live probe against the Compose stack passed 34 checks with all eight outboxes clean.
- **2026-10-15** — **Pawnshop**: seventh module `AuctionServer.Modules.Pawnshop` where an established player buys premises once the lifetime turnover reaches the configured threshold and installs one bot from a configured ladder (four tiers by default), upgrade-only and without a refund. Premises and bot purchases are an asynchronous payment saga with Wallets (`PawnshopPaymentRequested`/`PawnshopPaymentCompleted`/`PawnshopPaymentRejected`, gate check and debit atomic in `Wallet.PayForPawnshop`, which leaves turnover untouched). `PawnshopKeeper` (5 s loop) requests a spawn from Inventory on the bot's interval through `PawnshopStockRequested`/`PawnshopStocked` (priced on transient items), keeps each item in stock for `StockSellDelay`, then sells it automatically and pays `Round(price * PayoutRate, 2)` through `PawnshopPayout`, which counts toward turnover. Within the window the owner can withdraw an item, and Inventory mints it at the full price through `PawnshopItemWithdrawn`. One live pawnshop per player through a filtered unique index, a payout-rate snapshot per item and timeouts validated at or above the 10-minute dead-letter horizon. Five endpoints under `/api/pawnshop`, seven new integration events, four new tables (migrations `Initial_Pawnshop`, `Add_Pawnshop_Bot`, `Add_Pawnshop_Stock` and `Set_Pawnshop_Stock_Rate_Precision`), 89 test methods in the new project plus 17 handler and entity tests in Wallets and Inventory. A live probe against the Compose stack passed 33 checks.
- **2026-10-15** — **Bank loans**: sixth module `AuctionServer.Modules.Banking` with fixed loan offers from configuration gated by the new `Wallet.LifetimeTurnover` counter (economy credits only; transfers and starting funds excluded; migration `Add_Wallets_Turnover`), an asynchronous grant saga (`LoanRequested`/`LoanApproved`/`LoanRejected`, gate check and credit atomic in `Wallet.DisburseLoan`), a single repayment at maturity collected by `BankKeeper` (5 s loop) through `LoanRepaymentRequested`/`LoanRepaymentCollected` and best-effort `Wallet.CollectUpTo`, partial collection with a one-time penalty (`OverdueSince` marker) and automatic retries, early manual repayment via `POST /api/bank/loans/{id}/repayments`, one open loan per player through a filtered unique index, timeouts validated at or above the 10-minute dead-letter horizon; four endpoints under `/api/bank`, five new integration events, three new tables (migration `Initial_Banking`), 55 test methods in the new project plus turnover and loan-handler tests in Wallets.
