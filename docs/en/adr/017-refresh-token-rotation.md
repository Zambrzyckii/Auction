# ADR-017: Refresh token rotation

- **Status:** accepted (2026-11-15) · PL: [../../pl/adr/017-refresh-token-rotation.md](../../pl/adr/017-refresh-token-rotation.md)
- **Context:** a player JWT lives 15 minutes, and since the frontend kickoff of 2026-11-08 the client answered its expiry with a re-login ([ADR-015](015-angular-frontend-stack.md), [DECISIONS.md](../DECISIONS.md)), so a player could be logged out mid-action. Issue #18 asked for a refresh flow, and on 2026-11-15 the owner weighed three answers. An OIDC provider with Authorization Code and PKCE stays the target in [infrastructure.md](../infrastructure.md), but it would add a new service and a new login flow. A longer JWT lifetime needs no code, but the JWT is never revoked, so a stolen token would stay valid for its whole life. A refresh token rotated by Identity keeps the 15-minute JWT, needs no package on either side and gives the server a way to end a session.
- **Decision:** a player login returns `{ token, refreshToken }`. The refresh token is 32 random bytes in base64url, and the server stores only its SHA-256 hash in `IdentityRefreshTokens`, next to a `FamilyId` that every successor inherits. `POST /api/users/refresh` trades an active refresh token for a new pair in the same family, revokes the presented token, gives the successor an expiry seven days from now and removes that player's revoked or expired rows older than seven days. A token that is already revoked counts as reuse, so it revokes every active token of its family and answers 400 like an unknown or expired one, while the player's other devices keep their own families. `POST /api/users/logout` revokes the presented token when it is active and answers 200 with an empty body in every case, so it tells nothing about the token. Both routes are anonymous, because holding the refresh token is the proof, and the token travels in the request body, never in the URL the gateway logs. A bot gets `refreshToken: null` and keeps its 24-hour JWT. The client keeps both values in `localStorage` and renews the JWT a minute before its `exp` from a timer, at startup and before a request whose token is due. Tabs take turns through the Web Locks API and adopt a pair another tab rotated through the `storage` event, only a 400 from `/refresh` ends the session, and the running push stream survives a rotation ([frontend.md](../frontend.md)).
- **Consequences:** an active player is never logged out, and a session ends only through a logout, a detected reuse, a deleted account or seven days without a refresh. A response lost on the way, for example when a tab closes during a refresh, leaves the client holding a token the server has already revoked, so its next refresh counts as reuse and logs that device out. Two rotations of the same token that overlap in the database end with 409 for the loser through the `Version` concurrency token, and the family survives. An origin without HTTPS other than localhost has no Web Locks, so there two tabs can post the same token, and when the second request arrives after the first has committed it counts as reuse and logs that browser out, at once or at its next refresh. The JWT itself is never revoked, so a JWT copied before a logout or a family revocation keeps working until its `exp`, at most 15 minutes later. The refresh token sits in `localStorage` with the same exposure to XSS as the JWT already had. Dead rows are purged only when their owner rotates again, so a player online all day adds about 100 rows a day and keeps them up to seven days, and an account that logs in without ever refreshing, like the k6 seed players, keeps one row per login ([ARCHITECTURE.md](../ARCHITECTURE.md#known-limitations)). Sessions started before the deploy hold only `auction.token` and log in again after its `exp`, as before. An OIDC provider would replace this flow and its table.
