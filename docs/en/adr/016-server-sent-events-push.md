# ADR-016: Server-Sent Events push channel

- **Status:** accepted (2026-11-15) · PL: [../../pl/adr/016-server-sent-events-push.md](../../pl/adr/016-server-sent-events-push.md)
- **Context:** the Angular client shipped on polling alone: the auction detail every 2.5 s, the war detail every second during bidding, wallets every 5 s, lists and histories every 10 s, with exponential backoff on failures ([frontend.md](../frontend.md)). Every asynchronous outcome therefore reached the screen one poll late at best, and [frontend.md](../frontend.md) listed "no push channel" as the last API gap. The stage-three decision of 2026-11-14 ([DECISIONS.md](../DECISIONS.md)) chose a one-way nudge over data on the wire, and this record settles the transport. Three candidates were weighed. SignalR ships in `Microsoft.AspNetCore.App` but needs the `@microsoft/signalr` npm package (a new package, which [ADR-015](015-angular-frontend-stack.md) reserves for the owner's consent), opens with a negotiate POST that the host's `Writes` limiter would count, needs the `Upgrade` and `Connection` headers and a long `proxy_read_timeout` in nginx, and brings bidirectionality, groups and a Redis backplane that the synchronous writes of [ADR-008](008-synchronous-writes-outbox-boundary.md) never asked for. A raw WebSocket needs no package, but the browser API cannot set headers, so the token would travel in the URL (straight into the gateway's JSON access log) or in a first frame, and framing, heartbeat and reconnect would all be written by hand. Server-Sent Events need no package either: .NET 10 ships `TypedResults.ServerSentEvents` over `System.Net.ServerSentEvents`, a `fetch` with an `Authorization` header lands in the gateway's `authenticated` zone while the host limiter ignores GETs, and nginx needs one location with `proxy_buffering off` on the HTTP/1.1 it already speaks. `EventSource` was ruled out because it cannot set headers and would fall into the `anonymous` zone.
- **Decision:** the push channel is Server-Sent Events served by the host at `GET /api/push` behind the JWT, carrying nudges and never data. An event is `event: <Topic>` with `data: {"auctionId":"..."}`, `{"warehouseId":"..."}` or `{}`; the seven topics in `PushTopics` (`AuctionChanged`, `AuctionListChanged`, `WalletChanged`, `WarehouseChanged`, `LoanChanged`, `CasinoChanged`, `PawnshopChanged`) each name the poller the client should refresh, polling stays the source of truth and the fallback. Public events are broadcast to every connected stream and the client filters by the id it is looking at; private events go only to the user named in the event's `*UserId` field. The routing rule is that a nudge concerns the module that published the event, because only that module's state is saved at that moment, and the states of consuming modules arrive through ordinary polling. `PushRoutes.Build()` maps 18 of the 38 event types by `nameof`, like `IntegrationEventRecipients`: `AuctionActivatedEvent` and `AuctionFinishedEvent` broadcast `AuctionChanged` plus `AuctionListChanged`, `BidPlacedEvent` and `AuctionCancelledEvent` broadcast `AuctionChanged` only (a cancelled auction was `Pending` and never on the list), `WarehouseWonEvent` broadcasts `WarehouseChanged`, `AuctionSettledEvent` nudges the seller's and the winner's wallets, and the Wallets confirmations, `LoanRepaymentRequestedEvent`, `CasinoCashOutEvent`, the pawnshop payout and withdrawal and `PlayerLevelledUpEvent` nudge their one user; the five rejections, the requests, stock and item-lock events and `UserRegisteredEvent` send nothing. The nudges originate in `PushEventPublisher`, an outer decorator of `IIntegrationEventPublisher` wrapping `InstrumentedEventPublisher` (so `PublishDuration` keeps measuring the transport alone), built once by the `Decorate` local function in `Program.cs` for both transports, because publication always happens in the api process: after a successful hand-off it deserializes the row through `IntegrationEventTypes` and dispatches through `PushRoutes` to `PushConnections`, and any routing failure is logged and swallowed, because the outbox row is already on its way. A "Push" recipient in `IntegrationEventRecipients` was rejected (durable `DeliveryMessages` rows, retries and dead letters for volatile nudges, plus a third hop of 0 to 3 s that [performance.md](../performance.md) leaves no room for), and so was decorating `IIntegrationEventDispatcher` (the same locality today, a broker round trip later). The endpoint re-reads `ExpiresUtc` from `AuthenticateAsync` and answers 401 when the remaining lifetime is not positive, because the default `ClockSkew` of five minutes would otherwise admit an expired token whose stream ended at once in a loop; it yields `event: connected` immediately so the headers leave with the first item, sends `event: ping` after 15 s without any other event, and ends the stream on `RequestAborted`, on `IHostApplicationLifetime.ApplicationStopping` and when the token expires. `PushConnections` keeps one bounded channel per stream (`PushOptions.Default`: heartbeat 15 s, buffer 64 with `DropOldest`, 4 streams per user, the fifth closes the oldest), registered as a singleton with code constants like the keepers and overridden in tests through `ConfigureTestServices`. The gateway gets `location = /api/push { proxy_buffering off; }`.
- **Consequences:** the channel assumes one api instance; with several, an exclusive per-instance queue bound to `auctionserver.events` would replace the decorator as the nudge source. Consumer-side states still arrive by polling: war bids, a war's start and cancellation (refunds only), the release of the previous leader's lock, a rejected item lock cancelling an auction, the Wallets rejections, friends, invites (Profiles has no outbox) and transfers have no events at all, so "My auctions", "My wars" and those states converge on the existing rhythms, which stay unchanged. A nudge shortens the time from publication, not from the POST: auction events arise after a saga round, so the delay a player sees is the saga, not the push. An auction nudge that lands inside the 2 s TTL of the Auctions read cache ([ADR-009](009-hybrid-read-cache-in-auctions.md)) reads stale data, so the client refreshes again after the TTL. The stream occupies one of the browser's six HTTP/1.1 connections per host; one tab is the norm and several tabs are a future "leader tab" over `BroadcastChannel`. The token ends the stream, so the client reconnects while the token lives and stops when it has expired. `AuctionActivatedEvent` gains its first consumer, a volatile one that is not a delivery, so the known limitation about its missing handler stays true for the delivery pipeline. The stream is the host's first long-lived response, which is why `ApplicationStopping` is wired in: without it one open tab would hold every `docker compose restart api` for the full 30 s `stop_grace_period`. The gateway's default `proxy_read_timeout` of 60 s stays, because the heartbeat is 15 s. The Angular client that consumes the channel shipped the same day ([frontend.md](../frontend.md)), and since 2026-11-15 own auctions and the war history filter `AuctionChanged` and `WarehouseChanged` by the ids on their lists instead of refreshing on every `AuctionListChanged`.
