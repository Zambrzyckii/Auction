# ADR-005: OpenTelemetry with Prometheus, Tempo and Grafana, measured by k6

- **Status:** accepted (2026-10-22, landed 2026-10-23) · PL: [../../pl/adr/005-observability-and-k6.md](../../pl/adr/005-observability-and-k6.md)
- **Context:** the server-infrastructure plan adds a pooler, a cache and a broker, and each of them claims a performance or reliability effect. The codebase had no telemetry and no load tests, so every such claim would be a guess, and the gameplay phase left one known number (the 3-9 s outbox visibility lag) measured only by hand.
- **Decision:** the host wires OpenTelemetry behind an `Observability` configuration section (absent means disabled, enabled validates fail-fast like `Profiles:Storage`). Traces, metrics and logs leave over OTLP to an OTel Collector, which feeds Prometheus (metrics), Tempo (traces) and Grafana (the single viewing and alerting surface), all pinned in `compose.yaml`; the owner picked this industry stack over the lighter Aspire Dashboard to practice it. The sampler is a `ParentBasedSampler` wrapping `DropOrphanClientSpansSampler`, which drops every root span of kind `Client`: the eight outbox pollers and the keepers would otherwise flood Tempo with single-span traces every few seconds. Two narrower tag-based variants were tried first and failed against reality, the stable semantic conventions renamed `db.system` to `db.system.name`, and Npgsql supplies no `db.*` tags at span creation, which is the only moment a sampler sees. Publishing is measured by the `InstrumentedEventPublisher` decorator in the host, and the outbox processors call the static `OutboxMetrics` in `Shared.Integration` (counters per module plus a publish-lag histogram with bucket boundaries aligned to the 20/40/80/160/320 s retry tiers), the single module touch of the phase. k6 scenarios (`browse`, `bid-storm`, `mixed` with the `visibility_lag` trend) run from the Compose network against `http://api:8080`, classify the domain's expected 409s as expected and fail on thresholds chosen from the baseline recorded in [performance.md](../performance.md).
- **Consequences:** every later phase is judged by a before/after k6 run instead of intuition, and the resource limits (`api` 2 CPUs and 1 GB, `postgres` 1 CPU and 512 MB) are frozen for comparability. Background database polling is invisible in Tempo by design while still counted in metrics; a trace does not survive the outbox hop (asynchronous by construction), an accepted non-goal. The stack costs four extra containers and their configuration, a price the owner took knowingly; the k6 thresholds (p95 under 67 ms, failure rate under 1 percent, `visibility_lag` p95 under 6 s) now fail a run that would previously have degraded silently.
