# ADR-011: Delivery dispatcher between transport and handlers

- **Status:** accepted (2026-11-01) · PL: [../../pl/adr/011-delivery-dispatcher.md](../../pl/adr/011-delivery-dispatcher.md)
- **Context:** the architecture review before phase five showed that `IIntegrationEventPublisher` promised only "publish succeeded" while the system leaned on behaviors MediatR happened to provide: recipients ran in assembly registration order (money rules such as "Wallets charges before Inventory mints" hung on `Program.cs` line order), one failing recipient hid the event from the recipients behind it, and a consumer's exception travelled back to the producer's outbox row, whose retries and dead letters therefore recorded other modules' failures. RabbitMQ keeps none of these promises, because a broker publish returns before any consumer runs, so the planned transport swap would have changed system behavior while still compiling.
- **Decision:** publishing splits into transport and delivery. `PublishAsync` now means only "handed over for delivery": the in-process transport calls `IIntegrationEventDispatcher.AcceptAsync`, which writes one row per recipient into the shared `DeliveryMessages` table (`DeliveryDbContext` in `Shared.Infrastructure`, composite key `(MessageId, Recipient)` making the hand-off idempotent), and the producer's outbox row is marked processed at that moment. Recipients and their order live in one explicit host file, `IntegrationEventRecipients`, and the registry is strict: an event type without an entry throws. A single sequential `DeliveryProcessor` claims due delivery rows with the same leased `FOR UPDATE SKIP LOCKED` pattern as the outbox courier (ADR-010) and invokes each recipient's handler separately, so backoff retries and dead letters live per recipient. The hidden Wallets-before-Inventory ordering of `WarehouseWonEvent` became an explicit chain: Wallets emits `WarehouseSettledEvent` in the charging transaction and Inventory mints from that event, mirroring the auction settlement.
- **Consequences:** swapping the transport in phase five means an AMQP publisher plus a consumer that calls the same `AcceptAsync`, and the dispatcher tests (map order, one recipient's failure does not stop the others, a dead letter belongs to one recipient) must pass unchanged for both transports. Producer outbox metrics now measure the hand-off alone, and the new `AuctionServer.Delivery` meter measures handler work per recipient; the event path gained a second 3 s polling hop, measured on 2026-11-01 at about half a second on the median and 0.3-0.5 s on p95 (7.3-7.5 s against the 8 s threshold, see [performance.md](../performance.md)). A delivery row duplicates `Type` and `Content` per recipient, the same copy a broker queue would hold.
