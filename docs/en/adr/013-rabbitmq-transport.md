# ADR-013: RabbitMQ transport behind the publisher seam

- **Status:** accepted (2026-11-04) · PL: [../../pl/adr/013-rabbitmq-transport.md](../../pl/adr/013-rabbitmq-transport.md)
- **Context:** ADR-003 kept the event bus in-process behind `IIntegrationEventPublisher` and promised the broker as a drop-in replacement. ADR-011 then split transport from delivery, so publishing means "handed over for delivery" and retries with dead letters live per recipient in `DeliveryMessages`. Phase five brings the real broker. The planned bots ([bots.md](../bots.md)) consume market events from RabbitMQ and command only through HTTP (ADR-008). The delivery-split measurement showed that both 3 s polling hops stay whatever the transport, so the broker buys process separation and an external feed, not a lower visibility lag.
- **Decision:** the host, and only the host, talks AMQP through the raw `RabbitMQ.Client` 7.2.2 package. A messaging framework such as MassTransit or Rebus was rejected because it would duplicate the outbox, inbox and retry pipeline the repository already owns. A new fail-fast `Messaging` section switches the transport, with `InProcess` as the default, so `dotnet run` and every test fixture behave as before. `RabbitEventPublisher` publishes the outbox hand-off to the durable direct exchange `auctionserver.events` with routing key `delivery` into the durable queue `auctionserver.deliveries`. The metadata rides in the native AMQP properties `MessageId` and `Type` (the owner chose them over a JSON envelope), the body is the raw event JSON and the messages are persistent. The awaited publisher confirm means an outbox row is marked processed only once the broker has the message on disk. One channel guarded by a semaphore carries all eight outbox processors, and the connection is recreated lazily after a failure. `RabbitDeliveryConsumer`, a `BackgroundService` with a reconnect watchdog, consumes with manual acks and prefetch 20, feeds the same `DeliveryDispatcher.AcceptAsync` and acks only after the save. A failed accept is nacked back to the queue after a 5 s cooldown (the owner picked a loud requeue loop over a silently dropped message), and the broker keeps no retry state because ADR-011 keeps it in the database. Public market events additionally go to the durable topic exchange `auctionserver.market` with the type name as the routing key. The allowlist is the host's explicit `MarketEvents` set, fixed by the owner at four auction events (`AuctionActivatedEvent`, `BidPlacedEvent`, `AuctionFinishedEvent`, `AuctionCancelledEvent`), and the feed is consume-only for bots.
- **Consequences:** no module changed, the swap is two host classes behind the seam, which was the point of ADR-003 and ADR-011. Delivery across the broker is at-least-once, and every consumer side is already idempotent through the `DeliveryMessages` key and the apply-once inbox. Four tests on a Testcontainers broker prove the roundtrip, a redelivery after a failed accept, the market copy and the market silence for internal events. A broker outage makes `PublishAsync` throw `TransportUnavailableException` (hardening phase, 2026-11-07): the outbox processor releases the claimed leases, aborts the pass and counts no attempt, so pending rows simply wait out the outage and drain once the broker returns. Only a failure tied to the message itself burns attempts and dead-letters after five, and a parked row is revived with the runbook in [operations.md](../operations.md), backed by the `OutboxDeadMessages` and `OutboxPublishFailing` Prometheus rules. The compose stack runs the management image with the UI on `127.0.0.1:15672`, while the saga tests stay in-process on purpose, so the delivery guarantees remain covered identically for both transports.
