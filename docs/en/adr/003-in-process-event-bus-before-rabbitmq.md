# ADR-003: In-process event bus behind a publisher seam, RabbitMQ later

- **Status:** accepted (2026-08-26) · PL: [../../pl/adr/003-in-process-event-bus-before-rabbitmq.md](../../pl/adr/003-in-process-event-bus-before-rabbitmq.md)
- **Context:** RabbitMQ is part of the target system, but running a broker during the backend-only phase would add infrastructure without changing how modules are written.
- **Decision:** the outbox processors publish through `IIntegrationEventPublisher`; its first implementation, `InProcessEventPublisher` in the host, originally deserialized the row through `IntegrationEventTypes` and published it straight to MediatR handlers, and since 2026-11-01 it hands the row to the delivery dispatcher instead (see ADR-011). Since 2026-11-04 it is no longer the only implementation, because ADR-013 put the AMQP transport behind the same seam.
- **Consequences:** modules already assume at-least-once delivery and sequential handlers; swapping the transport means one AMQP publisher plus a host-side consumer feeding the same delivery dispatcher, a promise that was true of compilation from the start and is true of behavior since ADR-011 moved ordering, retries and dead letters out of MediatR defaults; that swap happened on 2026-11-04 exactly as described here (see ADR-013), and since then the market feed the planned bots will subscribe to exists on the broker.
