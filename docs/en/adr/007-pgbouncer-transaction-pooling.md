# ADR-007: PgBouncer transaction pooling between the api and PostgreSQL

- **Status:** accepted (2026-10-23, landed 2026-10-24) · PL: [../../pl/adr/007-pgbouncer-transaction-pooling.md](../../pl/adr/007-pgbouncer-transaction-pooling.md)
- **Context:** one connection string feeds the nine module `DbContext`s and the Dapper `SqlConnectionFactory`, and Npgsql's pool opens up to its default 100 physical connections, exactly PostgreSQL's default `max_connections`. A measured 30-second storm of 2000 requests per second drove the pool to all 100 connections and left them idle after the run, so even an administrative `psql` was refused with "sorry, too many clients already". One api instance can starve the whole database, and a second instance would find no free slot. The code is compatible with transaction pooling (no advisory locks, no session state, no LISTEN/NOTIFY, no prepared statements), and the migration lock of Npgsql EF 10 turned out to be `LOCK TABLE "__EFMigrationsHistory" IN ACCESS EXCLUSIVE MODE` inside the migration transaction (`LockReleaseBehavior.Transaction` in `NpgsqlHistoryRepository`), not the session advisory lock the plan first assumed, so migrations survive transaction pooling too.
- **Decision:** `edoburu/pgbouncer:v1.26.1-p0` joins the `data` network as the ninth service and the api reaches postgres only through `pgbouncer:6432`, startup migrations included, with one connection string and no separate `MigrationConnection`. `Infrastructure/pgbouncer/pgbouncer.ini` sets `pool_mode = transaction` with the owner's sizes, `default_pool_size = 25`, `reserve_pool_size = 10` (drawn after a 5 s wait), `max_db_connections = 40` as the ceiling across pools and `max_client_conn = 500`, so one api instance costs postgres at most 35 of its 100 slots. Authentication stays SCRAM, the image's entrypoint writes `userlist.txt` from `DB_USER` and `DB_PASSWORD`, and an unknown ini parameter is fatal at startup, verified live with a misspelled `max_db_connections`. The api keeps Npgsql pooling on and adds `No Reset On Close=true`, the Npgsql recommendation for transaction mode. The two pools do different jobs, Npgsql saves the TCP and SCRAM handshake per query while PgBouncer rations server connections, and without the flag every connection return would send a `DISCARD ALL` that wipes a server connection other clients share. The host now fails fast at startup when `ConnectionStrings:DefaultConnection` is missing instead of registering nine modules with a null string. The tests start the real image through Testcontainers. All nine contexts migrate from zero through the pooler, 40 parallel sleeping clients are served by exactly 25 server connections in `SHOW POOLS`, and ten concurrent registrations of one email give one 201 and nine 409s.
- **Consequences:** under the same storm postgres now peaks at 11 backends instead of 100 and returns there after the run, the latency tail collapses (p99 from 58 ms to 1.9 ms, max from 576 ms to 132 ms) and no iterations are dropped, at the price of about 7% of throughput (from 1738 to 1609 requests per second), because excess requests wait in the pooler's queue instead of competing inside postgres. At the regular loads the extra hop costs nothing measurable and the whole api is served by 3-4 backends (see [performance.md](../performance.md)). Session features are off limits from now on. An advisory lock, a temporary table or LISTEN/NOTIFY would land on a server connection other clients share, so whoever introduces one must first move that caller off the pooler. At one api instance the win is protection and readiness for replicas rather than speed, as the plan predicted. The concurrent-registration test also exposed that a taken email answered 400, so registration and bot provisioning now answer 409 through the new `EmailAlreadyTakenException`, an API contract change recorded in [backend/identity.md](../backend/identity.md).
