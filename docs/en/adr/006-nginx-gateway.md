# ADR-006: nginx gateway in front of the api, with IP limits and a CIDR trust model

- **Status:** accepted (2026-10-22, landed 2026-10-23) · PL: [../../pl/adr/006-nginx-gateway.md](../../pl/adr/006-nginx-gateway.md)
- **Context:** until phase two the api published its own port, so nothing stood between a client and the host. The platform needs one entry point for the planned frontend and bots and a place for IP rate limits and body caps that costs the host no work. Behind a proxy the host must still see the real client address and scheme, and the owner wants as much cross-cutting traffic control as possible moved out of the application.
- **Decision:** nginx 1.28.3 (alpine) is the only published service, and its whole configuration is one file, `Infrastructure/gateway/nginx.conf`. It proxies `/api/` and `/health`, answers `/gateway-health` itself, opens `/openapi/` only to loopback and the private ranges `172.16.0.0/12` and `192.168.0.0/16` and answers everything else with 404. Rate limits are per client address in three zones split by the presence of an `Authorization` header, anonymous at 20 requests per second (burst 40), authenticated at 60 (burst 120) and login with register at 1 (burst 5). Rejections come back as 429 with `Retry-After: 1` and a JSON body in the api's `{"error":"..."}` shape, and oversized bodies as 413 in the same shape. The default body cap is 64 KB and the avatar upload gets 4 MB, so the gateway is never stricter than the api. nginx overwrites `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Request-Id`, compresses JSON from 1 KB, writes a JSON access log without the `Authorization` header and re-resolves the api through Docker's DNS every 5 seconds. On the host a fail-fast `Gateway` section lists the trusted networks as canonical CIDRs (a typo like `172.16.80.1/24` is a startup error, as in Docker's own check), and `UseForwardedHeaders` runs first and trusts the whole pinned `edge` network `172.16.80.0/24`, so a second gateway would need no change. `/health/live` and `/health/ready` separate liveness from readiness, and the api container reports healthy through bash `/dev/tcp` on `/health/ready`. CORS stays in the host. The writes zone, the bot zone keyed on `X-Api-Key` and `limit_conn` from the plan were left out to keep the first version small. TLS is deferred.
- **Consequences:** every request from outside passes the limits, the body caps and the access log, and the api no longer has a published port (`compose.debug.yaml` publishes it on 127.0.0.1:8081 for debugging). nginx cannot verify a JWT, so a fake `Authorization` header buys the bigger bucket, and limits per user stay with the backend in phase 7. Inside Compose and on this machine every client shares one address, so k6 through the gateway is held to 20 anonymous requests per second, and the measured overhead is about 0.05 to 0.1 ms on the median (see [performance.md](../performance.md)). The edge range appears twice in `compose.yaml`, in the network and in `Gateway__TrustedNetworks__0`, and if the two drift apart the host silently stops trusting the headers. The `/openapi/` allow list works only while `edge` stays inside `172.16.0.0/12`. The avatar cap couples nginx to `Profiles:Avatar:MaxBytes`, so raising that setting towards 5 MiB needs the 4 MB limit raised too. A recreated api is found within one 5-second window of 502 responses, and nginx answers 502 with an HTML page instead of JSON. `Host` reaches the api without the port, which affects only the OpenAPI `servers` entry. Until TLS lands (HTTPS only with an own certificate, renewed automatically or served by a redundant pair) the stack must not face the internet.
