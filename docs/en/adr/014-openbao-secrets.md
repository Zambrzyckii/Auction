# ADR-014: OpenBao as the secrets backend

- **Status:** accepted (2026-11-04) · PL: [../../pl/adr/014-openbao-secrets.md](../../pl/adr/014-openbao-secrets.md)
- **Context:** until phase six every secret of the stack lived as a plaintext environment variable in the committed `compose.yaml`, and the dead `Backend/.env` pair suggested a mechanism that never existed. The application already reads all configuration through `IConfiguration`, so the missing piece was a configuration source backed by a secrets service. Plain compose file secrets cover most of the hygiene for the infrastructure containers, but they cannot express per-application access control or an audit trail, and the owner wanted the experience closest to a cloud Key Vault. Infisical was rejected as too heavy (its own database plus Redis), OpenBao (the Linux Foundation fork of HashiCorp Vault, MPL-2.0, Vault-compatible API) was chosen.
- **Decision:** the api reads its five secrets (`ConnectionStrings:DefaultConnection`, `Jwt:Key`, `Bots:ApiKey`, `Messaging:Rabbit:Password`, `Cache:Redis:ConnectionString`) from OpenBao through a hand-written `IConfigurationProvider` of about 120 lines, with no new package. VaultSharp and the bao agent were noted as alternatives and rejected because the provider needs exactly two HTTP calls, an AppRole login and one KV v2 `GET`. The fail-fast `Vault` section defaults to `Enabled=false`, so `dotnet run`, the tests and CI never need a vault, the same pattern as the `Messaging` transport switch of ADR-013. Enabled, the source is added last, so vault values win over environment variables, and every failure (unreachable, 403, 404, missing credential files, a non-string value) stops startup with a message naming the configuration key. The secrets live under `secret/auction/api` with the configuration keys, colons included, as the KV field names, so flattening is a plain copy. The AppRole policy, written by the owner, grants read on exactly `secret/data/auction/api`. Infrastructure containers do not talk to the vault, they get compose file secrets generated by `Infrastructure/secrets/gen-secrets.sh` into a gitignored directory. PgBouncer gets a mounted, generated `userlist.txt` instead of a wrapper image (the owner's pick, no second built image), Redis gets `--requirepass` from a file (the owner's pick, which makes the Redis connection string a real secret), and RabbitMQ gets a generated `conf.d` file because its image hard-rejects the `_FILE` environment variants. In compose a dev-mode `vault` service plus a one-shot `vault-init` seed the policy, the AppRole, the secrets and the `role-id`/`secret-id` files on every stack start, and the api waits for `service_completed_successfully`. The persistent raft mode with a manual unseal exists as the `compose.vault-persistent.yaml` overlay with its drill in [operations.md](../operations.md).
- **Consequences:** `compose.yaml` carries no secret values any more, only references, and the legacy `Backend/.env` files are gone. The api reads the vault once at startup, so rotation means editing a secret file and restarting the chain, documented in the runbook. A vault outage cannot corrupt anything, the api fails fast with a readable error and its restart policy retries until the vault returns, verified live. On a single host the gain is honestly mostly educational, the trust chain still ends on the host filesystem where `gen-secrets.sh` writes the files and the Docker volume holds the AppRole credentials, which is exactly the secret-zero problem named in the plan. Dev mode keeps the vault in memory, so every vault restart needs a reseed by `vault-init`, and the drill proved two sharp edges now handled in the script and the runbook, a fresh persistent vault has no KV engine mounted and dev mode refuses a root token in the `s.` service-token format. Tests cover the provider on a fake `HttpMessageHandler` and the real AppRole contract on a Testcontainers OpenBao.
