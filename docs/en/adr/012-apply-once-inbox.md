# ADR-012: Apply-once inbox operation

- **Status:** accepted (2026-11-01) · PL: [../../pl/adr/012-apply-once-inbox.md](../../pl/adr/012-apply-once-inbox.md)
- **Context:** the architecture review before phase five found the same read-exactly-once ritual copied into 39 of the 40 event recipients: check the inbox, apply the change, add the `ProcessedMessage` row by hand, save without a cancellation token, and swallow the module's `EventAlreadyProcessedException`. Under the ritual sat eight twin `ProcessedMessage` entities, eight `WasEventProcessedAsync` copies and eight twin exceptions, and the repositories translated **every** unique violation during that save into "already processed" without asking which index fired, so a real domain conflict guarded by another unique index (one active funds lock per auction, one profile per user) could be silently swallowed while the message was marked delivered. The handlers also imported `Infrastructure.Inbox` types into the Application layer, and RabbitMQ (phase five) will deliver duplicates more often than the in-process courier does.
- **Decision:** the inbox becomes one apply-once operation. The `ProcessedMessage` entity lives once in `Shared.Infrastructure/Inbox` (like the outbox since ADR-010), each module maps its own table through `ProcessedMessageModel.Configure`, and the shared `InboxOperation.ApplyOnceAsync` extension on `DbContext` runs the whole ritual: early return on a recorded `EventId`, the handler's change delegate (which may return one reply `OutboxMessage`), one `SaveChangesAsync(CancellationToken.None)` with the inbox row, and a swallow of **only** the unique violation whose `PostgresException.ConstraintName` equals the inbox primary key taken from the EF model. Each module's repository exposes a one-line `ApplyOnceAsync` forward, handlers state only what should change, and the eight per-module entities, `WasEventProcessedAsync` copies and `EventAlreadyProcessedException` types are deleted. Snapshots were hand-edited to the new CLR type; the tables did not change, so there is no migration.
- **Consequences:** "read exactly once" has one meaning per module instead of 39 private copies, and every new handler gets the correct behavior by construction. A foreign unique violation now propagates: the delivery row retries and dead-letters with the real reason instead of the message being silently dropped, which is a behavior change proven by the Profiles duplicate-profile test. In the duplicate race the losing transaction rolls back whole; when the loser also carried a reply row, its retry hits the early-return path, costing one extra delivery attempt in an already rare race. Application handlers no longer import module `Infrastructure.Inbox` types, and Profiles now references `Shared.Infrastructure` like every other module.
