# Wallets module

> English version. Polish 1:1 counterpart: [../../pl/backend/wallets.md](../../pl/backend/wallets.md)

`AuctionServer.Modules.Wallets` keeps the virtual money: one wallet per user with an available and a locked balance, created automatically on registration, charged and credited by the auction and shop events, and exposed through two endpoints under `/api/wallets`. It is the only module with both an inbox and an outbox that replies to an event with another event.

## Overview

| Area | Files |
|---|---|
| Endpoints | [`Presentation/WalletEndpoints.cs`](../../../Backend/src/AuctionServer.Modules.Wallets/Presentation/WalletEndpoints.cs), request record `AddFundsRequest` |
| Commands and queries | `Application/Command/AddFunds/` (command, handler, validator), `Application/Queries/GetWallet/` (query, handler, `WalletDto`), `Application/WalletsOptions.cs` |
| Event handlers | `Application/Handlers/UserRegisteredEventHandler.cs`, `BidPlacedEventHandler.cs`, `AuctionFinishedEventHandler.cs`, `ItemSoldToShopEventHandler.cs` |
| Domain | [`Domain/Entities/Wallet.cs`](../../../Backend/src/AuctionServer.Modules.Wallets/Domain/Entities/Wallet.cs), [`Domain/Exceptions/WalletExceptions.cs`](../../../Backend/src/AuctionServer.Modules.Wallets/Domain/Exceptions/WalletExceptions.cs) |
| Infrastructure | `Persistence/` (`WalletDbContext`, `WalletRepository`, `Migrations/`), `Configuration/`, `Outbox/`, `Inbox/`, `Background/OutboxProcessor.cs` |

[`WalletModuleExtensions.AddWalletsModule`](../../../Backend/src/AuctionServer.Modules.Wallets/WalletModuleExtensions.cs) takes the connection string and the starting funds, rejects a non-positive amount with `ArgumentOutOfRangeException`, registers `WalletDbContext`, the `OutboxProcessor` hosted service, a `WalletsOptions` singleton and `IWalletRepository` as scoped. The module is CQS rather than CQRS: reads use the tracked-free `GetUserWalletByIdAsyncReadOnly` (`AsNoTracking`), writes load a tracked wallet with `GetUserWalletByIdAsync` and save through one of the repository's save methods.

## Running

```bash
# from Backend/
dotnet ef migrations add <Name> --project src/AuctionServer.Modules.Wallets --startup-project src/AuctionServer.Api --context WalletDbContext --output-dir Infrastructure/Persistence/Migrations
dotnet ef database update --project src/AuctionServer.Modules.Wallets --startup-project src/AuctionServer.Api --context WalletDbContext
dotnet test tests/AuctionServer.Modules.Wallets.Tests
```

Migrations live in [`Infrastructure/Persistence/Migrations/`](../../../Backend/src/AuctionServer.Modules.Wallets/Infrastructure/Persistence/Migrations): `20260708083704_Initial_Wallets`, `20260815151947_Add_Wallets_Inbox` and `20260830054657_Add_Wallets_Outbox`. The test project contains the only concurrency tests in the solution (`WalletConcurrencyTests`: two contexts change the same wallet and the second save throws) and an API smoke test (`WalletApiSmokeTests`: `POST /funds` returns 200 for a `Bot` token and 403 for a `User` token).

## Configuration

| Key | Default | Effect |
|---|---|---|
| `Wallets:StartingFunds` | `300` (`appsettings.json`) | read by the host at startup and passed to `AddWalletsModule`, which stores it in `WalletsOptions(StartingFunds)`; `UserRegisteredEventHandler` credits it to every new wallet |

A missing value stops the host (`Missing configuration value 'Wallets:StartingFunds'`); a value of zero or less fails in `AddWalletsModule`.

## Data model

| Column | Type | Notes |
|---|---|---|
| `UserId` | `uuid` | primary key; equal to the Identity `PublicUserId` from `UserRegisteredEvent` |
| `AvailableFunds` | `numeric(18,2)` | money the user can bid with |
| `LockedFunds` | `numeric(18,2)` | money held for the auctions the user currently leads |
| `IsSuspendedWallet` | `boolean` | set only by `SuspendAccount`, which has no caller; the unique index on `UserId` is filtered on `"IsSuspendedWallet" = false`, but `UserId` is also the primary key, so that index adds no constraint |
| `Version` | `uuid` | concurrency token, regenerated by every money method |

The module also owns `WalletsOutboxMessages` and `WalletsProcessedMessages`, described in [messaging.md](messaging.md). The invariants live in the entity:

| Method | Rule | Effect |
|---|---|---|
| `AddFunds(amount)` | `amount > 0` | `AvailableFunds += amount` |
| `LockFunds(amount)` | `amount > 0`, `AvailableFunds >= amount` | moves `amount` from available to locked |
| `UnlockFunds(amount)` | `amount > 0`, `LockedFunds >= amount` | moves `amount` from locked back to available |
| `SpendLockedFunds(amount)` | `amount > 0`, `LockedFunds >= amount` | `LockedFunds -= amount`; the money leaves the wallet |
| `SuspendAccount()`, `UnsuspendAccount()` | — | toggle `IsSuspendedWallet`; no callers in `src/` |

| Exception | Status | Message |
|---|---|---|
| `InvalidAmountException` | 400 | `Amount must be greater than zero` |
| `InsufficientFundsException` | 400 | `Not enough funds on account` |
| `InsufficientLockedFundsException` | 400 | `Not enough locked funds on account` |
| `UserWithThisIdDontHaveWallet` | 404 | `User with this ID {id} doesnt exists` |
| `WalletAlreadyExistException` | 409 | `Wallet already exists` |
| `EventAlreadyProcessedException` | 409 | `Event was already processed`; raised by the repository and caught by the event handlers |

## API

| Method and route | Auth | Request | Response | Handler |
|---|---|---|---|---|
| `GET /api/wallets/{id}` | anonymous | `id` is the user's `PublicUserId` | 200 `{ availableFunds, lockedFunds }` (`WalletDto`), 404 when no wallet exists | `GetWalletQueryHandler` |
| `POST /api/wallets/funds` | JWT with the `Bot` policy | `{ amount }`, greater than zero | 200 with an empty body; credits the caller's own wallet | `AddFundsCommandHandler` |

`AddFundsCommandHandler` takes the wallet id from the `NameIdentifier` claim, calls `AddFunds` and saves with `CancellationToken.None`. There is no endpoint that moves money between users; every other balance change comes from an event.

## Events

| Direction | Event | Handler and effect |
|---|---|---|
| consumed | `UserRegisteredEvent` | `UserRegisteredEventHandler` creates `Wallet { UserId = PublicUserId }`, calls `AddFunds(StartingFunds)` and saves with `AddWalletAsync`; a unique violation becomes `WalletAlreadyExistException`, which is swallowed, so there is no inbox row for this event |
| consumed | `BidPlacedEvent` | `BidPlacedEventHandler` locks `NewPrice` on the new winner's wallet and, when `PreviousWinningUserId` and `PreviousPrice` are set, unlocks `PreviousPrice` on the previous winner's wallet; one `SaveUserFundsWithInboxAsync` |
| consumed | `AuctionFinishedEvent` | `AuctionFinishedEventHandler` returns when `WinnerUserId` or `FinalPrice` is null; otherwise `winner.SpendLockedFunds(FinalPrice)`, `seller.AddFunds(FinalPrice)` and an `AuctionSettledEvent` outbox row in one `SaveUserFundsWithInboxAndOutboxAsync` |
| consumed | `ItemSoldToShopEvent` | `ItemSoldToShopEventHandler` calls `AddFunds(Price)` on the owner's wallet; `SaveUserFundsWithInboxAsync` |
| published | `AuctionSettledEvent` | written by `AuctionFinishedEventHandler`; consumed by Inventory, which transfers the item |

Bots are registered through the same `UserRegisteredEvent`, so a bot wallet also starts with `StartingFunds`; the event carries no role.

## Decisions

- Balances can never go negative because every rule is checked inside `Wallet` before a field changes; the handlers and the repository add no arithmetic of their own.
- `Version` is a concurrency token regenerated on every money method, so two concurrent changes to one wallet end with one `DbUpdateConcurrencyException`; the concurrency tests pin this behaviour.
- All money writes pass `CancellationToken.None` to `SaveChangesAsync`, so a client that disconnects mid-request cannot leave a half-applied change.
- Reads and writes both use EF Core (CQS); the Dapper read path exists only in Auctions.
- Funds are locked after a bid is accepted and `LockedFunds` is a single aggregate number without a link to the bid, which is why a bid without coverage leaves the previous leader's money locked; the per-bid reservation is planned, see [../VISION.md](../VISION.md).
